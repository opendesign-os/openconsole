先判断要不要建

这一步被跳过的次数远超想象。知识库是基础设施，不是默认选项。

硬边界

语料小于 ~200K token（约 500 页）时不要做 RAG。直接把全部内容放进提示词，配合提示缓存，效果更好、链路更短，而且不存在「检索失败」这一整类故障。这是 Anthropic 在 Contextual Retrieval 一文里给出的明确建议。

0.1长上下文没有取代检索

两者解决的是不同问题，生产系统里是组合关系：检索把大语料收窄到一个子集，长上下文模型在这个子集上推理。

维度长上下文检索
擅长全局综述、跨章节推理、风格一致的改写定点查找、精确引用、海量语料里的针
规模受窗口与单次成本限制与语料规模解耦
新鲜度取决于请求时塞了什么索引更新即生效
权限难以按用户隔离可按租户 / 角色在检索内部过滤
成本曲线注意力随长度二次增长检索成本近似常数
可引用性需额外约束才能溯源天然带来源与定位

还有一个容易被忽略的事实：有效召回并不随窗口线性增长。窗口开大不等于模型真的用上了中间那段内容，相关研究普遍观察到长窗口中段的信息利用率明显下降，同时噪声被一并带入。

0.2三条必要条件

真正让检索不可替代的只有三条。一条都不占，就先别建。

  • 规模　语料远超可接受的上下文预算，且还在持续增长。
  • 新鲜度　内容频繁变动，要求分钟级而非重新部署级的生效。
  • 权限与可引用性　不同用户能看到的内容不同，或答案必须附可核查的出处。
常见误判

「我们有很多文档」不等于需要 RAG。先量一下总 token 数 —— 大量团队的全部内部文档加起来仍在单次上下文窗口之内，建知识库只是给自己增加了一条会失败的链路。

1

流水线的标准形态

成熟方案收敛到的形状基本一致，分摄入与检索两条链路。

1.1把计算挪到摄入期

摄入是离线的、可重放的，成本一次性摊给所有查询；查询期的每一步都要乘以 QPS。这条分界决定了系统的成本结构。

应当在摄入期只能在查询期
上下文增强、结构抽取、元数据归一化、同义词与缩写展开、分块、向量化、摘要生成、实体抽取 查询改写与指代消解、混合召回、融合排序、重排、上下文组装、生成

1.2摄入链路必须可重放

分块策略要改、embedding 模型要换、解析器要升级 —— 这些都会发生，而且会反复发生。

把原始文档与派生产物分离存储，派生层随时可以整体重建。做不到这一点，换一次模型就是一次数据迁移事故；做到了，换模型只是重跑一次摄入任务。

2

摄入侧

检索质量的上限在这里被确定，后面任何调优都只是在逼近它。

2.1解析：先把输入弄干净

所有分块策略在脏输入上都会退化。导航栏、Cookie 横幅、页眉页脚、断裂的表格标记，这些噪声会同时污染向量与倒排两路索引，后面补不回来。

工具定位许可取舍
DoclingIBM 开源，现属 LF AI & DataMIT纯 CPU 约 1.5 页/秒，工程化与版面还原最均衡；难扫描件不如专用 VLM
MinerUOpenDataLab，已切换 VLM 后端AGPL 系中文、科研与金融文档强；资源消耗高，需要 GPU 才有吞吐
Unstructured格式覆盖最广，30+ 种Apache 2.0通用性换来单类文档上的精度妥协，适合来源杂乱的场景
Marker基于 Surya OCRGPL 系（商用需注意）学术 PDF 针对性强，公式与参考文献处理好

选型原则

  • 先确定语料的主要形态，再选解析器。不要找「全能」方案 —— 混合语料用路由：按文件类型分派到不同解析器。
  • 统一输出 Markdown。标题层级是后续结构分块与元数据的唯一可靠来源，解析阶段丢了就再也拿不回来。
  • 表格单独处理。表格转成 Markdown 表格或行级自然语言描述，不要让它被当成普通段落切碎。
  • 剥离模板噪声。导航、页脚、版权、Cookie 提示在入库前去掉；这些内容在每篇文档里重复，会严重干扰 BM25 的词频统计。

2.2分块：结构优先，不要迷信语义分块

反直觉但证据明确

语义分块（semantic chunking）并没有稳定地赢过固定/递归分块。Vectara 在 NAACL 2025 的研究中，固定大小分块在文档检索、证据检索、答案生成三项上均优于语义分块，额外计算开销不被收益证明。多数独立评测也未能让语义分块在所有数据集上胜出。

默认参数

参数取值说明
策略结构感知递归优先按标题、段落、列表、代码块边界切，切不动再退回字符级

按内容类型调整

内容类型切分边界要点
散文 / 手册标题层级 + 段落标准递归即可，保留完整的标题路径

会议纪要 / 对话话题切换处保留发言人与时间，指代消解依赖它

chunk 是检索单元，不是生成单元

这是最值得单独记住的一条。检索命中一个小 chunk 之后，喂给模型的应该是围绕它扩展出的上下文 —— 相邻块、整节、或整个父文档。

2.3上下文增强：当前性价比最高的一招

独立 chunk 丢失上下文是检索失败的主因。「营收增长了 3%」这样的片段，脱离文档就无法判断说的是谁、哪一年、哪个口径。

Contextual Retrieval 的做法是在索引前，用 LLM 为每个 chunk 生成 50–100 token 的定位说明，拼在 chunk 前面，同时用于 embedding 和 BM25 索引。

实现要点

# 关键在于把整篇文档放进缓存，而不是为每个 chunk 重发
system: [整篇文档]          ← 缓存命中，只付一次
user:   这是文档中的一个片段：
        [chunk]
        请用 50-100 token 说明这个片段在文档中的位置与讨论对象，
        只输出这段说明本身。

# 产物拼接顺序
indexed_text = context + "\n\n" + chunk   ← 向量与 BM25 都用这一份
returned_text = chunk                        ← 返回给模型的仍是原文
成本前提

没有提示缓存，这个方案的成本会高一个数量级 —— 每个 chunk 都要重发整篇文档。先确认所用模型支持提示缓存再评估这条路线。

替代路线：late chunking

Contextual RetrievalLate Chunking
机制LLM 生成文字说明后拼接整文档 token 级 embedding，再按边界池化
摄入成本每百万 token 约 $1（需缓存）仅一次长上下文 embedding
收益覆盖向量路 + 词法路仅向量路
前提模型支持提示缓存embedding 模型支持长上下文
适用代词与跨章节指代多成本敏感、文档较短

两条路线目前没有在同一流水线里的严格对比，按上面的「适用」一栏选，不要同时上。

2.4元数据：决定了能不能上生产

字段必要性作用

权限必须前置

过滤必须发生在检索内部，不能是检索后在应用层筛。后筛会让 top-k 被无权访问的内容占满，表现为「有权限的用户搜不到东西」—— 这个 bug 在测试环境几乎不可见，因为测试账号通常有全量权限。

许可是 embedding 与 reranker 选型里最容易踩的雷。多个高分开源模型是 CC-BY-NC 或自定义研究许可，选型第一步先读 LICENSE，不是先看榜单。

embed 什么

一个常见错误是对原始源码或原始片段直接做 embedding。应当 embed 的是「意图 + 上下文」—— 实现细节会淹没意图，两段意图完全不同但写法相似的内容会被判为高相似度。

  • 代码：embed 函数签名 + 文档注释 + 用途描述，而不是函数体
  • 表格：embed 表头 + 行的自然语言化，而不是原始分隔符
  • 长文：embed 上下文说明 + 正文，而不是裸正文

维度与成本

Matryoshka 类模型允许在不重新训练的前提下裁剪维度。常见做法是用高维做重排前的精排、低维做大规模初筛，或者直接按召回评测结果选一个够用的维度。存储估算：

# float32
存储 ≈ 向量数 × 维度 × 4 bytes × (1 + HNSW 图开销 ≈ 0.5~1.0)

# 1000 万 chunk × 1024 维 ≈ 41 GB 裸向量，约 60~80 GB 实际占用
# 同样规模降到 256 维 ≈ 10 GB，int8 量化后再降约 4 倍
3

存储与索引

选型原则只有一条：引入最少的新基础设施。

3.1向量库选型

基准事实

一项同机、同数据集（118 万向量）、同 HNSW 参数的对比显示：在相同召回率下，不同向量库之间约有 2 倍查询延迟、4 倍磁盘、4 倍以上峰值内存的差距。这类运维差异比功能清单更值得关注。

方案形态适用规模取舍
pgvectorPostgres 扩展千万级以内事务、备份、权限全部复用，新增基础设施为零；超大规模吃力
Qdrant独立服务千万 ~ 亿级自托管性价比最优，元数据过滤与原生混合检索强
Milvus分布式集群十亿级GPU 加速与水平扩展；运维复杂度最高，小规模下资源占用明显偏大
Weaviate独立服务千万 ~ 亿级原生 BM25 + 向量混合，模块化生态完整
LanceDB进程内嵌入式百万 ~ 千万无服务端，向量 + 全文 + SQL 过滤 + 版本化，可直接写对象存储
sqlite-vecSQLite 扩展百万级以内纯 C 无依赖，SQLite 能跑的地方都能跑；仍是 pre-v1，有破坏性变更

绝大多数团队高估了自己的规模。千万级以内优先 pgvector —— 省下来的运维精力投到检索质量上，收益远高于换一个更快的向量库。

3.2词法索引必须同时建

只有向量索引的知识库一定会在精确标识符上失败。

典型失败

查询错误码 TS-999：embedding 会找到「关于错误码的内容」，但找不到这一个。函数名、型号、人名、版本号、配置项同理。BM25 做的是字面匹配，与向量是互补关系，不是备选关系。

实现上不需要额外组件：Postgres 有全文检索，SQLite 有 FTS5，Qdrant / Weaviate / LanceDB 内置 BM25。没有理由只建一路。

3.3索引参数

HNSW 的三个参数决定了召回与成本的平衡点，默认值往往偏保守：

参数作用调整方向
m每个节点的邻居数建索引时固定；16–32 常见，高维或高召回要求取大
ef_construction建索引时的搜索宽度越大索引质量越高、构建越慢；64–256
ef_search查询时的搜索宽度可在线调，是召回率的主要旋钮

一项小实例测试中，pgvector 的召回率仅靠调高 ef_search 就从约 95% 升到 98%。在换向量库之前，先确认当前这个的参数已经调过。

3.4增量更新

开源方案收敛到同一个结构：一张独立的记录表，与向量库并行维护。

CREATE TABLE index_record (
  doc_id        TEXT PRIMARY KEY,   -- 块级标识
  source_id     TEXT NOT NULL,      -- 所属文档，按来源批量清理用
  content_hash  TEXT NOT NULL,      -- 变更判定的唯一依据
  updated_at    TIMESTAMPTZ NOT NULL
);

每次摄入重新计算 hash：未变更的跳过，变更的重写，消失的删除。

三种清理语义

模式行为风险
incremental边摄入边清理适合按来源分批，中途失败影响面小；整源下线发现不了
full全部摄入完再清理加载器必须返回全量数据集，否则会删掉不该删的
scoped_full只清理本次出现过的 source_id 范围最安全的默认值，代价是内存里要记住这批 source_id；整源下线同样发现不了，需定期跑一次 full 对账

两个必须知道的陷阱

陷阱一 · 一致性

记录表与向量库是两套存储。记录写成功、向量写失败会留下静默不一致 —— 系统认为这块已索引，实际检索不到。要么做补偿重试，要么周期性对账。

陷阱二 · 换模型

更换 embedding 模型后 hash 没变，增量逻辑会全部跳过，结果是新旧向量混在同一个索引里。这种污染极难发现，表现为检索质量无端下降。

解法：把模型标识纳入 hash 计算。hash(content + metadata + model_id + chunk_params) —— 换模型或改分块参数时自动触发全量重建。

4

检索侧

混合召回打底，重排收口，上下文预算贯穿始终。

4.1混合检索与 RRF

向量召回与 BM25 召回并行，用 Reciprocal Rank Fusion 融合：

score(d) = Σ  1 / (k + ranki(d))        k = 60
         i∈检索器

# rank 从 1 开始；未命中的检索器对该文档不贡献分数
# k=60 来自原论文，直接沿用，几乎不需要调

RRF 按排名而非原始分数融合，因此不需要跨系统归一化分数 —— 这正是它成为默认选择的原因。BM25 的分数与余弦相似度本就不在同一量纲，任何加权求和都需要先解决这个问题，而 RRF 绕过了它。

多个独立评测显示，RRF 融合在全部指标、全部数据子集上优于任一单路检索。

4.2重排：单项收益最大的一步

共识非常一致：混合检索打底，加一个 cross-encoder 重排，是单步收益最大的改动。

Anthropic 的配置是召回 150 重排到 20；他们同时发现 top-20 明显优于 top-5 与 top-10。

模型许可取舍
Qwen3-RerankerApache 2.0开源权重质量第一梯队
BGE-reranker-v2-m3宽松部署量最大的稳妥默认值，多语言表现均衡
ms-marco-MiniLM 系列宽松延迟最低，质量明显下降；适合强延迟约束
ColBERT / late-interaction视模型质量好，但多向量使存储与延迟成本增加数倍
Cohere / Voyage API—省部署，按量计费，数据出境
不要照搬延迟数字

公开的重排延迟数据差异极大 —— 同类模型从个位数毫秒到数百毫秒的报告都有，取决于硬件、批大小与候选数。必须在自己的硬件和候选规模上实测，这是少数无法靠读资料替代的环节。

4.3查询侧处理

手段解决什么代价

4.4上下文预算是稀缺资源

检索结果应当分级返回：

  • 第一级　标识 + 一句话摘要 + 来源定位。用于让模型（或人）判断要不要看。
  • 第二级　按需取回完整内容。

给 Agent 用的检索工具尤其要这样设计。把完整内容一次性全塞回去，是 Agent 场景里最常见的 context 浪费 —— 模型往往只需要其中一条，却为全部付了代价，还要在噪声里挑。

5

图检索：什么时候才需要

解决的是单一问题，不是通用升级。

GraphRAG 针对的是答案需要跨多个文档聚合关系的问题 —— 「A 和 B 的关系经历了哪些阶段」、「这个概念在哪些模块之间传递」。普通向量检索对这类问题无能为力，因为答案不存在于任何单个 chunk 里。

方案许可取舍
Microsoft GraphRAGMIT参考实现，概念完整；索引阶段大量 LLM 调用，成本高
LightRAG开源知识图谱 + 向量检索结合，提供 naive / local / global / hybrid / mix 五种查询模式，成本显著低于前者
nano-graphrag开源最小实现，模块化易定制，适合读懂原理后自己改
判断标准

只有一条：你的问题是否需要跨文档关系聚合。如果多数问题是定点查找，图索引的建设与维护成本不会回本 —— 实体抽取与关系消歧本身就是一个需要持续维护的子系统。

先把混合检索 + 重排做扎实，遇到明确的关系型问题再上图。

6

评测：没有评测等于没有知识库

开源实践里最被跳过、也最致命的一环。

没有评测就无法判断任何改动是改进还是退步，调优会退化成玄学 —— 换个分块大小、换个模型、改个 prompt，全凭感觉。

6.1先建 golden set

50–200 条真实问题 + 标注的正确来源，由领域内的人写。规模不重要，代表性才重要。这个集合是所有后续决策的裁判。

  • 问题来自真实使用场景，不要让 LLM 凭空生成 —— 合成问题只能用来扩充，不能用来定义基线
  • 必须包含难例：精确标识符、跨文档、否定式提问、语料中不存在答案的问题
  • 「不存在答案」这类用例尤其重要，它测的是系统会不会编

6.2检索与生成分开评

聚合分数会掩盖问题 —— 检索错了和生成跑偏，看起来都是「答案不对」，但修复方向完全相反。

层指标回答什么
检索context recall该找到的内容找到了吗
context precision · MRR · nDCG@k找到的内容排得靠前吗
生成faithfulness答案是否忠于检索到的内容（反幻觉）
answer relevance答案是否真的回答了问题

6.3工具

工具形态适合
RAGAS指标库最常用，上述四类核心指标的 LLM-as-judge 实现
DeepEval测试框架pytest 风格，最容易接进 CI
TruLens追踪 + 评测链路可观测，RAG Triad 分析
BEIR检索基准检索器本身的横向对比，不评生成

目前没有单一框架形成统治，按形态选即可 —— 选哪个远不如「有没有」重要。

6.4放进 CI

分块参数、模型版本、prompt 的每一次改动都跑一次。没有这条回归防线，知识库的质量只会随时间单调下降：每个人都只改了一点点，没人知道是哪一次改坏的。

最小闭环

golden set（50 条）→ 检索指标脚本 → CI 上跑 → 指标下降超过阈值就拦住 PR。这套东西一天能搭完，比后面所有调优加起来都重要。

7

Agentic 与接入层

检索正在从「生成前的固定前置步骤」变成「模型可以反复调用的工具」。

模型自己决定检索几次、用什么词、要不要换个角度再查一次。这改变了接入层的设计重心：从「返回最好的结果」变成「让模型容易用对」。

设计理由
接受查询数组而非单个查询并行检索后去重。在工具描述里明确要求模型一次给出多个同义表达，比事后扩展更准
限制单次返回条目数通常 ≤ 5，防止 context 爆炸
详情按需获取完整内容默认不返回，由模型决定对哪几条深入
读写分离检索类只读工具与写入类工具彻底分开，权限与审计都更清晰
用工具描述约束行为把「先检索再回答」写进工具描述，比写在系统提示里有效得多
返回结构化失败原因「无结果」和「查询太宽泛」要可区分，模型才知道怎么重试
8

落地顺序

每一步都要能单独产生价值，不能等全套做完才见效。

1干净输入 + 结构分块 + 混合检索

解析统一成 Markdown，结构感知递归分块，向量 + BM25 双路 RRF 融合。不碰任何花活，这是后面所有优化的基线。

能稳定回答定点查找类问题，精确标识符不漏
2golden set 与评测闭环

在加任何新技术之前先建立度量。没有基线数字，后面每一步都无法判断是否有效。

CI 上能跑出检索指标，改动会触发对比
3加重排

单项收益最大，实现成本低。此时应该能在第 2 步建立的评测上看到明确提升。

context precision 明显上升，延迟仍在预算内
4上下文增强

Contextual retrieval 或 late chunking，二选一。摄入成本上升，但是一次性的。

跨章节指代类问题的召回提升可量化
5Agentic 检索与图检索

前者看 Agent 场景的实际需求，后者看是否真有跨文档关系型问题。两步都不该在前四步做扎实之前开始。

有明确且反复出现的需求，而不是「听说这个更先进」
9

反模式清单

以下每一条都在真实项目里反复出现。

反模式后果
只做向量检索精确标识符、错误码、专有名词全部检索不到
脏输入直接分块噪声污染双路索引，后续调优无法补救
没有评测就调参无法判断改动方向，调优退化成玄学
权限在应用层后筛top-k 被无权内容占满，表现为「有权限却搜不到」
换模型不重建索引新旧向量混杂，质量下降且极难定位
对原始源码 / 片段做 embedding实现细节淹没意图，相似度失真
chunk 即生成单元要么检索精度差，要么上下文不完整，二选一
语料很小仍上 RAG徒增故障点，效果不如全文入提示词
查询期做本该摄入期做的事成本乘以 QPS，延迟不可控
先上 GraphRAG建设与维护成本高，多数问题用不上
只看榜单不读许可上线前才发现模型禁止商用
照搬他人的延迟数字硬件与候选数不同，结论不可移植
