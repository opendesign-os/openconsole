@openconsole/graph · 算法原理与设计

把可变的图编译成 Int32Array，再在上面跑可中断的算法

这个包是类型化端口的有向图内核。编辑器里的图要能增删改、发事件、带字符串 id；算法要的却是紧凑的整数数组。这篇教程从存储讲到 30 多个算法，每一节都说明它为什么这样实现，以及换一种做法会在哪里出错。

可变与不可变分家编辑走 Graph，计算走 Structure，中间只有一次编译
算法只认契约六个只读字段，凑得出来就能跑全套算法
每一步都能停单步压在 O(deg) / O(V)，任何规模都能分帧
宁可报错中间态、负权、NaN、缺入向，一律不给看起来正常的答案

PART 01

存储：CSR 与索引空间

算法的速度先由数据怎么摆决定，后面每一章都建立在这一节的三条数组上。

1.1邻接表摊平成三条数组

最直观的图表示是「每个节点一个对象，对象里一个邻居数组」。它好写，但遍历一个节点的邻居要先解引用节点对象、再解引用数组，V 个节点就是 V 个对象加 V 个数组，缓存几乎每一步都失效。

压缩稀疏行（CSR）把全部邻接写进三条定长数组。节点 u 的出边占据 other 上的一段连续区间，区间边界记在 offset 里。

第三条数组 edge 把邻接槽映射回边序号。边权不直接塞进邻接槽，有三个原因：平行边要能各自带权；无向编译时一条边在两端各占一个槽，它们得指向同一个权重；换一套权重时 CSR 可以原样复用。

1.2建 CSR 是一次计数排序

编译器手里是一张弧表（每条边的两端），要把它按源节点分组。比较排序是 O(E log E)，但这里的键是 0 到 V−1 的整数，计数排序三遍 O(V+E) 就够了。

这段代码刻意写成裸循环。它是编译里最贵的单项，包成捕获四条数组的闭包就拿不到内联。编译器与子集视图共用同一个 adjacency()：两处各写一遍，迟早会在自环或无向的边界上分叉。

1.3算法在索引空间里进出

这条规矩一直延伸到外部接口：toposort 给 Int32Array，ranks 给按索引下标的 Int32Array，dominators 给 idom[u]。要名字时在边界上调一次 snapshot.names()。

PART 02

分层与编辑层

编辑要的是灵活，计算要的是不可变。把两者放在一个类里，就得在每次邻接查询上为前者付代价。

2.1四层各管一件事

输入不可变带来三件事。长跑任务中断后恢复，不会读到改了一半的图。快照能整份搬进 Worker。过滤、折叠、无向化、合并都在编译期一次做完，运行期没有谓词回调，也没有视图转发的开销。

2.2平行数组与稳定索引

编辑层里，节点与边都以整数槽位寻址，属性存在平行数组里。槽位由 Slots 分配：它维护「键 → 索引」与「索引 → 键」两张表，外加一条自由表。

槽位一旦稳定，就能当作一等公民公开出去。所以图同时提供三套访问口径：

口径例子用在
按 id，要哈希，给对象node(id) / edge(id)交互与查询
按槽位，无哈希，给对象nodeAt(slot) / edgeAt(slot)全图扫描
按槽位，无哈希，给整数forEachLink / forEachOutAt编译与增量

编译快照、打包、增量拓扑序全走第三种，这些路径上一次字符串哈希都不做。命名上 At 后缀一律表示「收槽位、不查 id 表」。

PART 03

Structure 契约

算法与图之间的全部约定，就是下面这六个字段。

interface Structure {
  readonly order: number;
  readonly size: number;
  readonly outbound: Adjacency;             // { offset, other, edge }
  readonly inbound: Adjacency | undefined; // 与 outbound 同一对象即无向编译
  readonly weight: Reals | undefined;     // 边权，省略即每条边按 1 计
  readonly cost: Reals | undefined;       // 点权，省略即每个节点按 0 计
}

3.1接口，而不是类

手写一条三节点链就能跑最短路，不经过 Graph：

const chain: Structure = {
  order: 3, size: 2,
  outbound: { offset: Int32Array.of(0, 1, 2, 2), other: Int32Array.of(1, 2), edge: Int32Array.of(0, 1) },
  inbound:  { offset: Int32Array.of(0, 0, 1, 2), other: Int32Array.of(0, 1), edge: Int32Array.of(0, 1) },
  weight: Float64Array.of(3, 4),
  cost: undefined,
};
settle(shortestPath(chain, 0, 2)); // { distance: 7, path: [0, 1, 2] }

3.3缺入向：报错，而不是降级

受这条约束的入口有 degrees、sources、isolated、components、cuts、dominators、prim、ancestors、bidirectional、reversed、predecessors。不受影响的有 toposort、kruskal、sinks：它们只用出向。

3.4两个零成本的派生

子集视图。subset(structure, keep) 只保留给定节点和两端都在其中的边，边权、点权按新序号重排，产出就是一个普通 Structure。它是 O(保留规模)；回 Graph 编一份过滤快照则是 O(V+E)，按分组逐个算时差一个数量级。

边权画像。一遍 O(E) 扫描能得出三个结论：是否全是非负整数、最大值、首条负权边。它决定最短路走哪种队列（7.2 节），也顺手拦下 NaN。画像记在以权重数组为键的 WeakMap 上：reversed() 每次产出新的结构对象却共享同一份权重，以结构为键的话，反向搜索每跑一次就要重扫一遍。

PART 04

编译与增量复用

编译器是可变图与不可变 CSR 之间唯一的桥，它也负责在图没怎么变时少干活。

4.1视图是编译选项

Snapshot.of(graph, {
  weight: (w) => w ?? 1,             // 边权
  cost: (n) => n.duration,            // 点权
  node: (id, n) => keep(id),          // 节点过滤
  collapse: [groupId],               // 分组折叠成单节点
  undirected: true,                  // 每条边在两端各出现一次
  outbound: true,                    // 只编出向，省一半内存
  merge: Math.min,                   // 平行边合并，权重两两聚合
  shared: true,                      // 落在 SharedArrayBuffer 上
  reuse: previous,                   // 增量重编译
});

4.2三个版本号，分开作废

复用还有几道前提检查：传进来的快照必须出自同一张图、没被翻转过、编译选项一致、层回调引用相同。不满足的一律只是没有加速，不会出错。快照对源图只持 WeakRef：它常常活得比图久，强引用会把整张图连同端口对象一起钉住。

4.3跨线程

快照的 data 只含 typed-array 与字符串数组，可以直接 postMessage。Worker 侧用 Snapshot.from(data) 还原，它会校验长度与值域：offset 从 0 起且单调、other[k] 不越界，错位的数据不会一路静默算到底。

只跑索引空间算法的 Worker 改搬 core：它不带 id 标签。标签是字符串数组，结构化克隆只能逐个深拷贝，大图上占掉整份克隆耗时的绝大部分。多个 Worker 要零拷贝共享，就用 shared: true 直接编译到 SharedArrayBuffer 上。

PART 05

Task：可中断的调度

图算法全是同步的。要它们不冻结界面，就得能在任意一步停下来，过一帧再接着跑。

5.1中间状态全在实例上

interface Task<T> {
  advance(budget: number): boolean; // 推进至多 budget 步；false 表示已跑完
  readonly settled: boolean;
  readonly progress: number;         // 0..1
  result(): T;                      // 没跑完抛 Incomplete
}

中断只是停止调用 advance，再调一次就从原处接着跑。自家的算法继承 Stepwise，只实现 step() 与 measure()：完成标记、预算记账、进度归一都归基类。进度归一放在基类里是有原因的：提前终止（摸到终点、图不连通）时「已处理 / 总数」到不了 1，非连通图上的 Dijkstra 会停在 0.5，进度条永远差一口。

5.2单步粒度是硬约束

5.3驱动与组合

入口做什么
settle(task, signal?)同步跑完；每 4096 步检查一次中断，中断抛 Interrupted，现场保留可续跑
run(task, signal?)异步跑完，不让出事件循环；同步与异步任务都收
schedule(task, { budget, onProgress })分帧推进，帧间 setTimeout 让出；最后一帧会报出进度 1
chain(first, next)串联两个阶段，后一段由前一段的结果构造；阶段交接时就返回，一次 advance 不会花掉两倍预算
transform(task, convert)变换结果，不改变推进节奏

异步侧是平行的 Future，语义与 Task 逐条对齐，只是每一步可以 await。两套类型而不是一个 boolean | Promise<boolean> 联合，是因为后者会在每个同步驱动点埋雷：while (task.advance(Infinity)); 遇到 Promise 恒为真，直接死循环，而类型上毫无异样。

最短路

一套 Dijkstra 加五个变体。它们共用同一组判断：选哪种队列、何时提前停、负权怎么报。

7.1Dijkstra 不做 decrease-key

7.2桶队列还是堆

7.3一套实现，几种路径语义

Dijkstra 的贪心只要求一件事：combine(total, step) >= total，也就是沿路径走，代价不会变小。满足这一点的语义都能共用同一份实现：

const sum: Combine = (total, step) => total + step;                    // 常规最短路
const bottleneck: Combine = (total, step) => step > total ? step : total; // 最大边权最小的路线

settle(shortestPaths(snapshot, s, { combine: bottleneck }));

默认的加法在内层循环里走特化分支（this._adding ? base + cost : combine(base, cost)），不付每条边一次的间接调用。

7.6负权：Bellman-Ford 与 Floyd-Warshall

Dijkstra 遇到负权边直接抛 Negative，并点名改用 bellmanFord：负权下贪心不成立，硬跑只会给出错误的距离。

floydWarshall 求全源最短路，矩阵是 8·V² 字节，V=10000 就是 763MB。分配前先过一道规模闸门，默认上限 512MB，超限抛 Oversized 并报出申请量。它的一步是「一个中转点的一行」，O(V)（见图 12）；铺底也拆成每步一行。跑完后检查对角线，出现负值即有负环。

PART 08

连通、割与支配

四个都是基于 DFS 的经典算法，这里全部改写成了迭代版，状态压在平行 Int32Array 上。

8.1弱连通与强连通

弱连通忽略方向：从未标记的节点出发，沿出边和入边一起扩张。缺入向时只能沿出边走，得到的是按可达性分组而不是弱连通分量，所以它走 mirror（见图 9）。起点用 seek 挑：游标只增不减，整趟扫描摊销 O(V)，每轮从 0 重找就是 O(V²)。

condensation 在 SCC 之上把每个分量收缩成一个节点，得到无环的凝聚图。分量间的边按 from · count + to 去重：count 小于 2²⁶ 时这个键不超过 2⁵³，精确无误。

PART 10

增量拓扑序

编辑器里每连一根线都整图重排一次，代价是 O(V+E)。Pearce-Kelly 只动受影响的那一小段。

10.1只在两端之间重排

插入边 x → y 时，如果 rank[x] < rank[y]，现有顺序已经满足它，什么都不用做。这是编辑器里最常见的情况。只有逆序时才需要重排，而且受影响的只是位次落在 [rank[y], rank[x]] 之间、与两端相连的节点：

全部状态按整数槽位存：位次是一条 Int32Array（存「位次 + 1」，0 表示不在跟踪范围，省掉一条并行的有效位图），冲突边是一个数字 Set，区域搜索走 forEachOutAt。compact() 之后按 compacted 事件给的映射原地搬运，不整图重算。

它订阅图事件，所以放在编辑层一侧，不在 algorithm/ 目录里。

PART 11

设计原则与验证

前十章里反复出现的几个判断，以及测试是怎么把它们钉住的。

11.1宁可报错，也不给看起来正常的答案

下面这些位置，恰恰是错答案最容易骗过人的地方。NaN 最典型：它与任何值比较都是 false，于是连通的节点被报成不可达。

错误何时抛不抛的话会怎样
Incomplete任务没跑完就取结果把未收敛的中间值当成答案
Oneway需要入向，结构只编了出向弱连通分量被拆开、生成树漏分支
NegativeDijkstra 遇到负权边贪心不成立，距离静默错误
Invalid边权或点权是 NaN连通节点被报成不可达
Oversized稠密结构超过内存上限静默吃掉上 GB 内存
Stale快照编译后源图又变了在旧结构上算出过期结果
Cycle拓扑序遇环、负环给出一个不成立的顺序

报错的时机也有讲究。跑遍全图的算法在入口一次性验掉 NaN，内层循环不必逐边再判；提前终止的搜索逐边现取现验，因为预扫往往比实际访问的边还多。

11.2依赖方向写成断言

tests/unit/layering.test.ts 读源码里的 import 语句，断言三件事：algorithm/** 一个文件都不 import graph / compile / snapshot；array / ident / slots / socket 的 import 列表为空；算法之间的相互依赖恰好只有一条，reach → {component, search}。往某个算法里塞一段公共代码再从另一个模块 import，测试立刻变红。

同一个测试文件还真打一次包：入口只导出 scc / settle / toposort 时，产物里不许出现 Graph、Journal、Snapshot、pack 等符号。配一条反向对照：导出 Graph 的入口必须把它们抓出来，否则「什么都没漏」可能只是检测本身失灵了。

11.3算法靠差分对拍

tests/naive.ts 里每个算法都有一份照定义直写、只用公开查询的朴素实现。随机图上把 scc、components、dominators、cuts、closure、最短路的结果与它逐一比对，8 个 seed 各跑一遍。一边是 Pearce、Tarjan、Lengauer-Tarjan 这类带巧思的迭代版本，一边是一眼看得懂的笨办法，哪一侧出错都会暴露。

11.4复杂度闸门只钉不随机器变的量

  • 计数最可靠：单步粒度就数推进步数；「有没有为每个节点付固定重成本」就数 JSON.stringify 调用次数。退化前后常常同阶、只是常数不同，耗时比与噪声重叠，只有计数分得开。
  • 同机同轮的对照量：删边路径拿建图当标尺，排干一张图理应比建它便宜得多。健康时排干只占建图的 15%–60%，退化成平方则是 4.3–8.3 倍，两侧各有一个数量级的余量。
  • 同进程的规模比（规模翻 4 倍，耗时不许涨过 9 倍）只用在编译与最短路这类比值确实稳定的地方。删边路径曾经用过，但缓存与 GC 让线性操作的常数也随数据量增长，4 倍规模实测能涨到 9.1×，与平方的 16× 贴在一起，并行跑整个工作区时必然误报。
